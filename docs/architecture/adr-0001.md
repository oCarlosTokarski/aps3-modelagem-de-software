# ADR 0001 — MQTT 5 (EMQX) para Ingestão de Telemetria dos AGVs

**Status:** Aprovado
**Data:** 2026-11-10
**Autor:** Carlos Tokarski Borges Neto
**Funcionalidade:** Sincronização de Telemetria e Detecção de Anomalias

## Contexto

Cada AGV envia posição, nível de bateria e velocidade **1 vez por segundo**. Com uma frota de até 60 veículos no parque industrial, são cerca de 60 mensagens/s em regime normal, com picos maiores quando os AGVs reconectam após uma queda do Wi-Fi industrial. A rede dos galpões tem **zonas de sombra** (estruturas metálicas), então as conexões caem e voltam com frequência.

Requisitos:

1. Baixo consumo de banda e de bateria no AGV (cabeçalho pequeno, conexão persistente).
2. Detectar rapidamente quando um AGV some (heartbeat / desconexão abrupta).
3. Escalar horizontalmente o Serviço de Telemetria sem duplicar mensagens.
4. Permitir comandos no sentido inverso (servidor → AGV), como a ressincronização.

Alternativas avaliadas:

| Opção | Prós | Contras |
|---|---|---|
| HTTP/REST (AGV faz `POST` a cada 1 s) | Simples, familiar | Cabeçalho grande, nova conexão TLS a cada envio, sem canal servidor → AGV |
| WebSocket direto na API | Bidirecional | Gerenciar milhares de conexões na API; sem QoS nem *Last Will* |
| Apache Kafka direto dos AGVs | Alta vazão, retenção | Cliente pesado para firmware embarcado; overkill para 60 msg/s |
| **MQTT 5 com broker EMQX 5** | Protocolo leve para IoT, QoS 0/1/2, *Last Will*, assinaturas compartilhadas | Mais um componente de infraestrutura para operar |

## Decisão

Adotamos **MQTT 5** sobre **TLS (porta 8883)** com o broker **EMQX 5** como canal entre os AGVs e o backend:

- **Telemetria periódica** (`agv/{agvId}/telemetria`): **QoS 0**. Perder uma leitura é aceitável porque a próxima chega em 1 s; isso evita retransmissões que congestionam a rede ao voltar de uma zona de sombra.
- **Eventos e comandos** (`agv/{agvId}/estado`, `agv/{agvId}/sync`): **QoS 1** (entrega pelo menos uma vez; o consumidor é idempotente pelo `timestamp`).
- **Last Will and Testament (LWT)** registrado no `entry / conectarBroker(LWT)` do AGV: o broker publica `agv/{agvId}/lwt` se a conexão cair, complementando o `WatchdogHeartbeat` de 5 s.
- **Assinatura compartilhada** `$share/telemetria/agv/+/telemetria`: várias réplicas do Serviço de Telemetria dividem as mensagens sem duplicação.
- Integridade: cada leitura é assinada com **HMAC-SHA256** (chave por AGV); leituras com assinatura inválida ou `timestamp` fora de ordem são descartadas.
- Os alertas **já processados** saem do Serviço de Telemetria para o **RabbitMQ 3.13 (AMQP)**, que é o barramento interno: o MQTT fica restrito à borda com os veículos.

## Consequências

**Positivas**

- Cabeçalho MQTT mínimo (2 bytes fixos) e uma conexão TLS persistente por AGV, o que economiza bateria e banda.
- Detecção de queda em segundos (LWT + watchdog), alimentando a transição `Operacional → Offline` da máquina de estados do `VeiculoAGV`.
- Escalabilidade horizontal do serviço Go por assinatura compartilhada.
- Canal bidirecional nativo para comandos (`/sync`, `/comando`, `/missao`), reaproveitado pelo despacho.

**Negativas / riscos aceitos**

- Mais um componente crítico (EMQX) para monitorar; mitigado com cluster de 2 nós.
- QoS 0 aceita perder leituras isoladas; decisões críticas (bateria < 15%) só são tomadas a partir de leituras válidas e consecutivas.
- Duas tecnologias de mensageria (MQTT na borda, AMQP no interior) exigem conhecimento dos dois protocolos pela equipe.
- Gerenciar as chaves HMAC por AGV (rotação, provisionamento) vira uma responsabilidade operacional.
